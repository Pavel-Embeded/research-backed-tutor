# 从空白独立构造项目

在规划教学终点和检查模拟初学者的独立输出时使用。项目是检验知识迁移的实际产物，不是装饰性的应用介绍。保持用户明确要求的任务和项目形态，不擅自改成更容易通过的东西。

## 定义高质量目标

把“能手写世上最好的项目”落实为严谨、可比较的标准：功能覆盖、正确性、边界与失败处理、结构清晰、适用的性能指标、解释能力、可复现性与扩展能力。调研可访问的优秀参考，注明其版本、许可、运行条件和实际读到或测到什么；对不可比较的指标写未验证，不凭声誉宣布胜出。

建立 `项目需求 → 知识节点／边 → 讲解位置 → 初学者实现 → 检查证据`。所有核心分支都要通过项目功能、推导、实验或独立分析得到验证；单个项目难覆盖的部分配子作品。未参与中心项目的必需知识仍要单独检验。

分别写清数学／理论定义域、程序或装置的输入契约、当前环境的资源边界，以及用户要求的覆盖范围。资源错误不使一个原本合法的输入自动变成错误输入；若需求包含它，就保留为未满足项并寻找可行改进，不能事后改契约掩盖失败。

## 项目形态要适合学科

| 主题类型 | 可从空白构造的产物 | 典型验证 |
| --- | --- | --- |
| 编程／算法 | 可运行实现、接口、示例数据、测试与说明 | 独立预期结果、空输入、边界、错误输入、复杂度与故障定位 |
| 数学 | 完整推导、证明或求解工具，配不同条件与反例 | 条件检查、独立计算、形式检验或可用工具交叉核查 |
| 工程／实验 | 设计、模型、实现或实验装置的适用部分 | 仿真、数据、测量、约束与实物分别记录；无法实测标未验证 |
| 人文／社会科学 | 带证据的研究作品、注释、时间线与竞争解释 | 原始材料对应、来源独立性、因果／相关区分、反方解释与反证 |
| 设计／创作 | 作品与设计理由、迭代版本及适用评估 | 需求覆盖、观察证据、可用性与对照，不把主观审美说成全球最优 |

非编程主题不强塞代码；用户明确要求软件或实物时不能拿论文或方案替换已要求的可运行／可实测产物。

## 教学与独立构造分开

先教必要工具、步骤、知识机制、接口和验证方法，并示范较小或不同的例子。随后给初学者空白环境、项目要求、已教内容和运行框架，隐藏导师完成版源码、标准答案和最终图谱。

初学者必须亲自写出核心算法、逻辑、证明或分析。能使用已明确说明的通用运行库，不得调用“一行替你完成核心知识”的黑箱来冒充理解；例如检验排序原理时不能只调用现成排序函数。

实际产物应包括目标、范围、结构／接口、输入输出、核心实现、设计理由、运行或复现步骤、测试／证据、已知限制和扩展路径。完整模板由导师代填不算独立产物。

## 检查与返修

1. 核验者独立确定预期结果与失败标准，不从初学者自己的输出倒推出“正确答案”。
   核验预期本身有独立依据；发现冲突先复核预期、检查器与实现，再决定修订哪一项。
2. 检查普通情境、新情境、边界、错误／反例、故障定位及所有必需指标；软件运行实际命令，实物要求相应测量，文献作品逐项核对证据。
3. 挑选一个变更任务，例如增加约束、改变输入形态、删除一个前提或制造一个缺陷，要求初学者自己调整并解释影响。
4. 任一错误回到讲解：补齐缺少的条件、算法、工具、关系或验证方法，再让初学者重新构造受影响部分，用新案例重测。

当前实现不满足需求时，先评估并教授可行的替代结构，保持原失败案例作为回归项；不能把可修正的实现缺陷包装为环境不可用，也不能删除困难的合法输入。确实需要改变用户明确要求的方法或交付形态时，报告方案差异，不能暗中替换。

禁止把“文件存在”“语法正确”“自己说可以”当作完整验收。禁止编造测试、性能、硬件或用户实测。达不到必需验证时标为未验证并保留缺口，不能说项目已经完成或“全世界最好”。

向真实用户提供空白任务、分层提示和可检查标准；把参考实现与答案放在练习之后，方便用户在不看答案的情况下亲手重做。
